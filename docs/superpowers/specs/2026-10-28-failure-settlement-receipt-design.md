# 升仙失败结算持久回执设计

日期：2026-10-28  
依据与 API 边界见 [失败结算证据](../../evidence/failure-settlement.md)。
范围：只处理已提交 FAILED 的三气失衡后果，不开放普通升仙路线，不改灾劫分类与成窍规则。

## 已确认的约束

- 原著证据仅支持人气、天气、地气三种明确过盛导致的致命失败；原因必须唯一且明确。TRIBULATION_IMPACT、UNCLASSIFIED 和混合原因继续拒绝。
- 碎窍失败为终态；不得自动撤销、恢复空窍或给普通单空窍玩家重试。
- 世界会话文件、玩家 NBT、死亡掉落与统计没有共同原子事务；不能声称这些 Minecraft 副作用在任意断电下 exactly-once。
- LivingDeathEvent 可取消且发生在掉落处理前；不作为死亡完成回执。
- PlayerEvent.Clone 仅在死亡克隆时可作为候选观察点。它触发时新玩家尚未进入 PlayerList，不能在该事件里依赖 saveAll() 保存新玩家；必须等 PlayerRespawnEvent。
- 玩家收据写入 NeoForgeData/PlayerPersisted，复用本体已有的持久子树复制语义。shiqiao 只是本体普通布尔字段，不是失败收据。
- 按用户要求，本设计和当前实现阶段均不启动 Minecraft、客户端、集成世界或专用服务器。

## 目标语义

自动处理最多进行一次同步失败结算尝试。若已能验证死亡克隆和玩家收据，则写入完成收据并确认世界会话；如果持久证据不足或各存档冲突，转入 UNCERTAIN，保留失败记录、禁止自动再次伤害、报告待人工核定。系统优先避免重复致死，不伪称每个崩溃窗口都能自动判定结果。

普通升仙门禁必须保持关闭。此协议即使实现，也只有通过后续隔离世界的进程退出、登录、死亡、重生和玩家存档验证后，才可评估是否具备开启失败能力的条件。

## 持久记录

### 世界会话

在失败原因已有持久记录的前提下，增加失败结算子状态和稳定操作 ID：

- PREPARED：唯一原因、会话 UUID 和终态修订已提交，尚未开始玩家侧尝试。
- STARTED：玩家侧同一操作 ID 的写前收据已验证；是否发生死亡仍未知。
- UNCERTAIN：有过一次尝试或数据冲突，但没有可信完成收据。不得自动再次致死。
- ACKNOWLEDGED：匹配的玩家完成收据已保存并核对，世界终态确认完成。

操作 ID 固定由升仙会话 UUID 与失败终态修订派生，恢复时不能生成新 ID 绕过“一次尝试”。

### 玩家 NBT

在 NeoForgeData/PlayerPersisted 下保存模组专属收据，至少包含操作 ID、单一失败原因与状态。状态为 STARTED 或 RESPAWN_RECEIPT。旧版失败记录没有稳定操作 ID 时，迁移为 UNCERTAIN，禁止旧恢复钩子再次造成死亡。

## 处理顺序

1. 服务端提交 FAILED、失败原因与 PREPARED；只有三种唯一白名单原因可进入后续策略。
2. 写入玩家 STARTED 收据及 shiqiao=true，调用公开保存路径，再读取实际玩家 NBT 核对 UUID、操作 ID、原因、状态和 shiqiao。单人房主同时核验 level.dat/Data/Player 的实际加载来源。saveAll() 正常返回不单独视作保存成功。
3. 玩家收据核对成功后，先把世界会话推进到 STARTED 并确认该写入成功；失败时不调用伤害，后续发现玩家 STARTED 收据而世界仍 PREPARED 时隔离为 UNCERTAIN。然后为该玩家和操作 ID 建立短期内存关联，在原有三种本体伤害类型中执行一次同步失败结算序列。
4. 尝试期间的 LivingDeathEvent 只在内存中记录当前玩家和操作 ID 的死亡事件观察；事件本身可取消，因此不得持久化为完成。若 hurt/kill 序列返回后玩家仍存活、出现异常或无法确定结果，将世界状态记为 UNCERTAIN；停止本次自动处理并保留诊断信息。
5. 只有真实死亡随后触发 PlayerEvent.Clone，且 wasDeath、原玩家写前操作 ID 与本次同步死亡事件观察均匹配，才将新玩家 PlayerPersisted 收据改为 RESPAWN_RECEIPT。Clone 回调不调用 saveAll()；若进程重启使内存关联丢失，即使触发 Clone 也不能据此确认，必须隔离为 UNCERTAIN。
6. 在之后的 PlayerRespawnEvent 中，新实体已加入 PlayerList。保存新玩家，读取并核对正确加载源中的 NBT 回执；确认操作 ID、原因与 RESPAWN_RECEIPT 全部匹配后，才把世界记录标为 ACKNOWLEDGED。
7. 世界 ack 写盘失败时保留 RESPAWN_RECEIPT。后续登录只允许重试“验证收据并确认世界记录”，不得再次施加伤害。
8. 登录发现只有 STARTED、操作 ID/原因不匹配、读盘失败或单人与 UUID 文件冲突时，持久隔离为 UNCERTAIN，不自动伤害、不删除失败证据。状态查询展示操作 ID 与两侧状态；人工核定不由本设计自动完成，也不能把不确定记录默认为已死亡或允许再次致死。

## 恢复表

| 世界状态 | 玩家收据 | 恢复行为 |
| --- | --- | --- |
| PREPARED | 无匹配收据 | 可开始一次写前准备流程 |
| STARTED / PREPARED | 匹配 STARTED | 转 UNCERTAIN；不自动再伤害 |
| STARTED | 无匹配收据 | 转 UNCERTAIN；不自动再伤害 |
| 任意未确认状态 | 匹配 RESPAWN_RECEIPT | 只补世界 ack；不伤害 |
| UNCERTAIN | 任意缺失、冲突或未知收据 | 仅报告并保留，等待人工核定 |
| ACKNOWLEDGED | 任意 | 终态，不再执行副作用 |

## 失败处理与迁移

- 写前玩家 NBT 未核对通过：不调用伤害；保留 PREPARED 或升级为 UNCERTAIN，下次先重新读取证据。
- PlayerDataStorage.save 的日志/返回不能视为确认；必须解析 UUID 玩家文件与单人房主的当前加载源。
- LivingDeathEvent 被取消、hurt/kill 后玩家仍存活或异常：标记 UNCERTAIN，不自动重试。
- 玩家克隆和收据保存成功但世界 ack 失败：安全重试 ack。
- 不可解析的旧 pending 状态和不匹配操作 ID 均隔离，绝不猜测成成功。
- 普通路线 readiness 与 CANONICAL_FAILURE 能力在本实现中维持空集/关闭。

## 验收

### 纯 Java 与离线检查

- 状态机覆盖合法迁移、重复事件、过期操作 ID、旧存档迁移、冲突收据、落盘失败和 UNCERTAIN 后禁止自动伤害。
- 验证 FAILED 原因与结算操作 ID 不会因普通状态更新改变；ack 幂等但不能绕开玩家收据。
- Java 21 全源码编译、核心回归、协议回环、客户端隔离与产物 Verify 通过。

### 运行验收（未来另行授权）

- 使用全新隔离存档验证：写前保存失败、死亡取消、正常死亡/重生、Clone 后崩溃、Respawn 保存失败、世界 ack 失败、重登补 ack。
- 验证死亡相关掉落、玩家统计和正常其他来源死亡不会被误判；每种不确定状态都不会自动二次致死。
- 真实服务器/客户端测试前需用户另行解除“不要开服务器”的限制；本轮不执行。

## Spec 自审

- 状态图没有宣称跨文件 exactly-once；只有匹配并验证的玩家完成收据才能推进世界 ack。
- STARTED 后无收据一律隔离，避免恢复代码把 PREPARED 与“死亡可能已经发生”混为一谈。
- 取消事件只作瞬时观察；实际完成需 Clone 的死亡语义、当前进程内的操作关联和 Respawn 后的持久核对同时成立。
- Clone 与 Respawn 保存顺序、单人房主加载源以及旧 pending 迁移均已明确；任何来源冲突都失败关闭。
- 人工核定没有偷渡成自动 retry 或自动 ack；本规格不打开路线，也不声称无需未来隔离世界验收。
- 未发现 TODO/TBD 占位内容。
- UNCERTAIN 只提供状态与审计信息；本规格不提供自动清除、确认已死或再次致死的管理员命令。需人工处理时，保留备份并单独审查数据，不把审计判断伪装成系统确认。

## 明确不做

- 不按客户端动画或客户端状态推断死亡、奖励或失败结果。
- 不对 TRIBULATION_IMPACT 使用三气过盛的伤害映射。
- 不保证跨玩家文件、世界存档、实体掉落与统计的原子 exactly-once。
- 不因本协议完成而自动开放升仙路线。
