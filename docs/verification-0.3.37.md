# 0.3.37 验证记录：纳气小游戏

日期：2026-11-01。基线 0.3.36。同轮完成了首次端到端升仙（见 `verification-e2e-success.md`）。

## 小游戏设计

**问题**：原调气页是三个输入框 + 提交按钮，玩家要"算数字"，体验像填表；而原著的纳气是持续手动平衡（CANON-002：人气稍重则自爆、天气稍多则消融、地气稍浓则石化）。

**做法**：把三个输入框换成三条可拖拽的**速率轨道**。

- 每条轨道上：实心条 = 服务端返回的当前气量（0..64 映射满格）；下方细条上的方块 = 玩家设定的抽纳速率（0..1）。
- 拖动轨道即时设定该气速率，松手提交一次 `QiIntentPayload`（服务端仍完全权威，界面只是发送与命令路径相同的负载）。
- 平衡带：`tolerance = max(0.18, 均值 × 2%)`——气量越大带越紧，对应"稍即致命"。
- 超带的气条变红并显示"已失衡"；风险值直接显示在标题行。
- **"速率配平"按钮**：一键把人气设成天地的 4/3。这是本轮实机踩出来的关键：人气释放上限 3.0/刻，天地吸收上限 4.0/刻，**同样的意图增量带来的增长不同**，玩家必须理解这个比才能活。

## 未验证

- 小游戏的**实际操作手感**未验证：需要把游戏窗口切到前台后按 K 打开（本轮截图时按键在窗口聚焦前发出，界面没弹出）。拖拽与"速率配平"按钮的实际点击行为、轨道命中区域是否好点，都还没有人摸过。
- 平衡带宽度 `max(0.18, 均值×2%)` 是新增的游戏映射，与服务器端 `QiParameters.balanceTolerance`（固定 0.18）**不完全一致**：界面按比例收紧只是视觉提示，真正的判定仍在服务端用固定 0.18。这个不一致要么统一，要么在文档里明确"界面只是提示"。已在此记录，待确认。
